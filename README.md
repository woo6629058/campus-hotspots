## 2주차: HTML과 페이지 연결

### 소개 장소

1. **니콜스관 4층 카페 하랑** — 넓은 창가에서 공부하거나 쉬기 좋은 곳
2. **하늘동산** — 벚꽃과 계절의 변화를 느끼며 산책하기 좋은 곳
3. **베리타스관 중앙도서관** — 시험과 과제를 준비하며 조용히 집중하기 좋은 곳

## 3주차: CSS와 반응형 UI

### 페이지별 스타일

- 프론트페이지: 추천 방문 순서를 색으로 따라갈 수 있도록 `page-home`에 하랑의 흰색·크림·베이지와 은은한 캐러멜, 하늘동산의 벚꽃·연두, 중앙도서관의 회백·푸른 회색·남색이 위에서 아래로 이어지는 그라데이션을 적용했습니다. 제목 글자에도 흰색에서 벚꽃색까지 이어지는 그라데이션을 사용하고 배경에는 부드럽게 흐르는 색 띠를 더했으며, 각 장소 카드는 장소 분위기에 맞는 강조색과 둥근 모서리, 부드러운 그림자로 구분했습니다.
- 니콜스관 4층 카페 하랑: 햇빛과 원목 가구의 포근함을 표현하기 위해 `page-cafe`에 크림·캐러멜 계열 그라데이션과 커피 김을 닮은 곡선 장식, 둥근 모서리와 부드러운 그림자를 적용했습니다.
- 하늘동산: 벚꽃과 새잎이 보이는 계절감을 표현하기 위해 `page-garden`에 하늘색·분홍색·연두색 그라데이션과 원형 빛, 유기적인 모서리와 부드러운 간격을 적용했습니다.
- 베리타스관 중앙도서관: 조용한 열람실의 차분함을 표현하기 위해 `page-library`에 회백색에서 푸른 회색을 거쳐 짙은 잉크색·남색으로 선명하게 이어지는 그라데이션과 책장을 닮은 얇은 직선 패턴, 명조 계열 글꼴과 반듯한 테두리를 적용했습니다.

### 모바일 스타일

- 적용한 `@media` 조건: 화면 너비 `640px` 이하
- 모바일에서 특별히 바뀌는 부분과 이유: 모바일에서는 본문과 카드의 여백, 제목과 소개 글의 크기를 줄이고 링크의 높이와 너비를 늘려 누르기 쉽게 만들었습니다. 모든 이미지는 화면 너비를 넘지 않으면서 원본 비율을 유지합니다.
- 휴대전화 확인 결과: 네 페이지 모두 한 열로 표시되며 가로 스크롤 없이 이미지와 링크를 사용할 수 있습니다.

### 실습 1 - 네 페이지를 하나의 탐험 화면으로
- 내가 수정한 부분: 2주차에 고른 카페 하랑, 하늘동산, 베리타스관 중앙도서관의 사진·설명·추천 활동을 한 화면의 세 `section`에 모았습니다. 장소 선택 버튼은 JavaScript에서 만들고, 첫 접속에는 카페 하랑이 선택되도록 했습니다.
- 버튼 클릭 → 내용 변경 → 지도 변경의 흐름: `app.js`의 `selectPlace()`가 선택하지 않은 `section`에는 `hidden`을 적용하고, 버튼의 `aria-pressed`를 바꾼 뒤 Google 지도 `iframe`의 `src`와 제목, 새 창 링크를 같은 장소 정보로 교체합니다.
- 휴대전화에서 확인한 결과: 화면 너비 390px에서 버튼·설명·사진·지도가 한 열로 표시되고 가로 넘침 없이 장소 세 곳을 전환할 수 있습니다.

### 실습 2 - 내가 발견한 데이터를 두 가지 시각화로
- 데이터 출처 URL / 내려받은 날짜: [공공데이터포털 · 전국도서관표준데이터](https://www.data.go.kr/data/15013109/standard.do) / 2026년 9월 21일
- 데이터 선택 이유 / 대상·기간·단위: 공부 장소와 연결되는 공공도서관의 지역별 차이를 살펴보기 위해 선택했습니다. 서울특별시 204개관, 인천광역시 119개관, 경기도 307개관으로 총 630개관이며 기관별 데이터기준일자는 CSV에 함께 보존했습니다. 그래프 단위는 개관과 %입니다.
- 그래프 1: “공공도서관이 많은 시군구는 어디인가?” / `시도명`, `시군구명`, `도서관명` / 지역 이름이 길고 여러 시군구를 비교하기 쉬운 가로 막대그래프 / 서울·인천·경기 버튼을 누르면 선택 지역의 모든 시군구 집계와 해석이 함께 바뀝니다.
- 그래프 2: “평일 21시 이후 운영하는 도서관 비율은 시군구별로 어떻게 다른가?” / `시도명`, `시군구명`, `평일운영종료시각` / 시설 수가 다른 시군구를 공정하게 비교하기 위한 비율 가로 막대그래프 / 표준 시각 열이 21:00 이상인지 비교하며, 실제 방문 가능 시간은 각 도서관의 최신 안내를 확인해야 합니다.
- 필터링·집계·결측치 처리: 전국 자료에서 `시도명`이 서울·인천·경기이고 `도서관유형`이 공공도서관인 행만 남겼습니다. 시군구명과 도서관명이 없는 행은 전체 분석에서 제외하고, 평일 종료 시각이 비어 있거나 올바른 `HH:MM` 형식이 아닌 행은 두 번째 그래프의 분모에서만 제외합니다. 결측치를 임의로 0으로 바꾸지 않습니다. 집계할 때 시군구명의 불필요한 접두어·공백과 명백한 오타 1건을 정리합니다.
- 지역·탭 전환 방식: `data-region` 버튼으로 서울·인천·경기 행을 고른 뒤 두 그래프와 해석을 다시 계산합니다. `data-panel`과 `section`의 `id`를 연결해 선택한 그래프만 보이게 하고, 두 버튼 그룹 모두 `aria-pressed`로 선택 상태를 알립니다. 숨겨진 그래프를 표시한 뒤 `requestAnimationFrame()`에서 차트 크기를 다시 맞춥니다.
- 휴대전화에서 지역 버튼과 두 탭을 확인한 결과: 화면 너비 390px에서 버튼, 그래프 범례·축, 해석과 출처가 화면 밖으로 나가지 않고 세로로 읽힙니다. 경기도의 31개 시군구는 그래프 높이를 항목 수에 맞게 늘려 이름이 겹치지 않게 했습니다.
- 빈 데이터·잘못된 CSV를 넣었을 때 결과: 파일 요청 실패, 필수 열 누락, CSV 해석 오류, 선택 지역에 분석 가능한 행이 없는 경우 그래프 대신 상태 영역에 원인과 확인할 항목을 표시합니다.
- LLM 활용: 공개 표준데이터의 지역 필터링, CSV 집계·지역 선택·탭 전환·오류 처리를 구성하는 데 도움을 받았습니다. 대표 질문은 “`시도명`, `시군구명`, `평일운영종료시각` 열을 사용해 서울·인천·경기의 시군구별 도서관 수와 21시 이후 운영 비율을 계산하고, 결측치를 0으로 만들지 않는 Chart.js 화면을 작성해 줘”였습니다. 원본 630개 행과 지역별 집계값을 직접 대조하고, 지역·탭 전환과 오류 메시지를 브라우저에서 검증했습니다.

### 실습 3 - 상상한 게임을 LLM과 만들기
- 게임 이름 / 아이디어 / 조작과 규칙: **별자리 산책로 미니 게임**. 밤의 캠퍼스에 흩어진 별을 1번부터 순서대로 선택해 빛나는 길을 완성하는 30초 게임입니다. 별 하나를 연결하면 +100점, 별자리를 완성하면 단계별 보너스를 받습니다. 순서를 틀리면 기회가 하나 줄고, 기회 세 개를 잃거나 30초가 지나면 끝납니다. 마우스와 터치로 조작합니다.
- LLM 활용: “HTML Canvas와 JavaScript로 밤의 캠퍼스에 흩어진 별을 번호 순서대로 연결하는 게임을 만들어 줘. 마우스·터치를 지원하고 점수·시간·기회·단계, 종료 결과와 재시작을 보여 줘. 단계가 올라갈수록 연결할 별을 늘리고 재시작할 때 이전 애니메이션을 정리해 줘.”
- 추가 수정 요청과 개선한 점: 별을 단순히 누르는 데서 끝나지 않도록 연결된 별 사이에 빛나는 선을 그리고, 다음 별에는 맥동 효과와 마우스를 따라가는 점선을 표시했습니다. 단계를 완성하면 별 개수가 하나씩 늘어나고 보너스 점수를 받도록 개선했습니다.
- 직접 확인한 동작: 번호 순서 선택, 별과 연결선 표시, 정답 점수 증가, 잘못된 순서의 기회 감소, 단계 전환, 30초·기회 소진 종료, 다시 시작할 때 점수·시간·기회·단계와 애니메이션 초기화를 확인했습니다.
- 휴대전화에서 확인한 결과: Canvas가 화면 너비에 맞게 축소되며 별을 손가락으로 누를 수 있고, 넓은 터치 판정 범위를 사용해 작은 화면에서도 선택하기 쉽습니다. Canvas 내부를 누를 때 의도하지 않은 화면 스크롤도 발생하지 않습니다.
- 이미지·소리 출처와 이용 조건: 외부 이미지와 소리를 사용하지 않고 Canvas 도형과 글자로 직접 표현했습니다.

## 5주차: 브라우저 상태
### 실습 - 나만의 취향 밸런스 게임
- 게임 주소: <https://woo6629058.github.io/campus-hotspots/week5/>
- 게임 이름과 소개: **같이 여행 가도 괜찮을까?** — 여덟 번의 선택을 통해 자신의 여행 성향을 알아보고, 같은 기기에서 참여한 친구와 답을 비교하는 여행 취향 밸런스 게임입니다.
- 게임의 대상과 주제를 선택한 이유: 친구와 여행을 준비하는 대학생을 대상으로 했습니다. 일정·숙소·식사·예산처럼 실제 여행에서 의견이 갈리는 상황을 미리 비교하고 대화할 수 있어 여행을 주제로 선택했습니다.
- 기본 예제에 없는 질문 최소 4개: 숙소 선택 기준, 여행지의 아침, 맛집 대기, 우연히 발견한 골목, 여행 예산, 풍경 사진, 길을 잘못 들었을 때를 포함해 총 8개 질문을 직접 구성했습니다.
- 직접 만든 결과 이름·설명과 선택의 연결: 계획 성향 선택이 많으면 `든든한 루트 설계자`, 두 방향이 정확히 4개씩이면 `유연한 여행 조율자`, 즉흥 성향 선택이 많으면 `설렘 추적 탐험가`가 됩니다. 각 결과에는 성향 설명과 추천 여행법을 제공합니다.
- 나만의 표현 한 가지와 구현한 위치: 친구와 답이 다른 문항마다 두 취향을 함께 반영할 수 있는 `타협 아이디어`를 비교 결과에 표시합니다. `week5/app.js`의 각 질문 데이터와 `renderComparison()`에 구현했습니다.
- 결과 분류 규칙과 동점 처리: 계획 성향 선택은 0점, 즉흥 성향 선택은 1점이며 답의 방향이 드러나지 않도록 A·B 위치를 문항마다 섞었습니다. 8개 답변의 합이 4보다 작으면 계획형, 4이면 균형형, 4보다 크면 즉흥형으로 분류합니다.

### 저장 설계

- sessionStorage에 저장한 값과 이유: `week5.travel.draft`에 참여 ID, 질문 버전, 별명, 현재 문항과 답변 객체를 저장합니다. 같은 탭에서 새로고침해도 작성 중인 여행 선택을 이어가기 위해 사용합니다.
- localStorage에 저장한 값과 이유: `week5.travel.history`에 완료한 참여 기록을 최근 20개까지 배열로 저장합니다. 탭을 닫은 뒤 다시 방문해도 결과 목록과 친구 비교 기록을 복원하기 위해 사용합니다.
- 내 데이터 조회·개별 삭제·전체 삭제 동작: 조회 버튼을 누를 때 두 저장소를 다시 읽어 임시 답변과 완료 기록을 구분해 보여줍니다. 개별 삭제는 선택한 기록만 배열에서 제외해 다시 저장하고, 전체 삭제는 이 게임의 두 키만 `removeItem()`으로 삭제한 뒤 화면 상태도 초기화합니다.

### 확인 결과

- 브라우저와 실험 조건: Chrome의 로컬 HTTP 환경과 화면 너비 390px에서 기능과 반응형 배치를 확인했습니다.
- 새로고침 / 독립적인 새 탭 / 탭 닫기 비교: 같은 탭에서 새로고침하면 진행 중 답변이 복원되고, 독립적인 새 탭에서는 임시 답변이 분리되지만 같은 origin의 완료 기록은 공유되는 것을 확인했습니다. 탭을 닫고 다시 방문했을 때는 완료 기록만 남았습니다.
- 중복 저장 / 잘못된 데이터 / 삭제 후 재방문 확인: 참여 ID를 기준으로 같은 기록이 중복 저장되지 않는 것을 확인했습니다. 잘못된 JSON·자료형·질문 ID·선택값에는 복구 안내가 표시되었으며, 삭제한 데이터는 새로고침 후에도 다시 나타나지 않았습니다.
- 브라우저 저장값을 신뢰할 수 없는 이유: 사용자가 개발자 도구에서 값을 직접 수정할 수 있고 저장소 접근이나 쓰기가 실패할 수도 있으므로, 성적·권한·개인정보처럼 중요한 데이터에는 사용할 수 없습니다.
- 적용한 방어 방법: JSON 해석을 `try...catch`로 처리하고 자료형·질문 버전·질문 ID·선택값을 검사합니다. 별명은 `textContent`로 표시하며 저장 실패 시 현재 실행은 유지하면서 안내합니다.
### LLM 활용

- 도움받은 작업: 강의의 필수 조건을 점검하고 여행 주제의 질문·결과·친구 비교, 브라우저 저장·복원·삭제·오류 처리 코드를 구성하는 데 도움을 받았습니다.
- 대표 질문 한 개: “여행 취향을 주제로 질문 8개와 세 가지 결과를 만들고, sessionStorage 이어하기, localStorage 최근 20개 기록, 친구 비교와 서로 다른 답의 타협안을 포함해 5주차 조건에 맞게 구현해 줘.”
- 직접 수정·검증한 내용: 질문과 결과 문구를 검토하고, 새로고침·친구 재참여·비교·개별 삭제·전체 삭제·모바일 화면을 직접 확인했습니다.

## 6주차: HTTP와 Flask 시작

- 이미지 처리 배포 주소: Render 배포 후 기록 예정
- 이미지 처리 로컬 주소: <http://127.0.0.1:5000/>
- 서버 TTS 로컬 주소: <http://127.0.0.1:5000/tts>

### 실습 1 · 이미지 처리

- 휴대폰 확인 화면: 로컬 390px 화면에서 원본·윤곽선 결과와 시간이 세로 한 열로 표시되고 가로 넘침이 없음을 확인했습니다. 배포 후에도 휴대전화에서 같은 동작을 다시 확인할 예정입니다. [확인 화면](week6/screenshots/image-result-mobile.png)
- 내가 수정한 내용: 제공 예제의 세 처리 방법과 form/fetch 흐름을 유지했습니다. 원본·서버 결과·처리 시간을 단계별 카드로 구분하고 데스크톱과 모바일에서 한눈에 비교할 수 있도록 반응형 디자인을 적용했습니다.
- 브라우저가 보내는 값 / 서버가 돌려주는 값: 브라우저는 `FormData`에 JPEG/PNG 파일, `operation`, Blur용 `kernel`을 담아 `POST /api/process`로 보냅니다. 서버는 입력을 검사하고 OpenCV로 계산한 PNG를 반환하며 `X-Compute-Ms`, `X-Processing-Ms`, `X-Image-Size` 헤더에 측정값을 함께 보냅니다.
- 세 처리 방법의 결과: Grayscale은 색을 명암으로 바꾸고, Gaussian Blur는 선택한 홀수 커널 범위의 주변 픽셀을 반영해 부드럽게 만들며, Edge Detection은 Canny 100·200 임계값으로 주요 경계를 표시합니다.
- 크기·커널을 바꿔 측정한 시간 표: 같은 샘플 이미지를 두 크기로 만들고 각 조건을 6회 실행한 뒤 첫 실행을 제외한 OpenCV 계산 시간의 평균을 기록했습니다.

| 이미지 크기 | 커널 3 | 커널 15 | 커널 51 |
|---|---:|---:|---:|
| 480×300 | 0.04 ms | 0.34 ms | 6.61 ms |
| 960×600 | 0.18 ms | 1.18 ms | 19.23 ms |

### 실습 2 · 서버 TTS

- 실행 명령: `python -m flask --app tts_app run --debug --port 5000`
- 사용한 모델 이름·언어·출처: 영어 `en_US-lessac-low` / [Piper 음성 모델 카드](https://huggingface.co/rhasspy/piper-voices/blob/main/en/en_US/lessac/low/MODEL_CARD)
- 내가 정한 사용 상황과 추가한 요소: 해외여행에서 바로 쓸 영어 문장을 연습하는 상황을 정했습니다. 길 찾기·맛집 추천·숙소 체크인 예문 버튼을 누르면 입력란에 문장이 채워지고 읽기 속도도 선택할 수 있도록 추가했습니다.
- 서로 다른 문장 두 개의 파형·길이 확인: 길 찾기 문장은 3.31초·103.5 KiB, 맛집 추천 문장은 3.10초·97.0 KiB로 생성되어 문장에 따라 길이와 WAV 크기가 달라지는 것을 확인했습니다.
- 생성 시간·음성 길이·WAV 크기가 보이는 결과 화면 스크린샷: [결과 화면](week6/screenshots/tts-result.png)
- 요청·응답 확인 기록: 브라우저는 영어 문장과 `length_scale`을 JSON으로 `POST /api/tts`에 보내고, 서버는 Piper가 생성한 `audio/wav`와 `X-Processing-Ms`를 반환합니다. 브라우저는 WAV `Blob`을 `AudioContext`로 분석해 길이와 Canvas 파형을 표시합니다.

### LLM 활용

- 도움받은 작업과 대표 질문: 6주차 필수 조건을 확인하고 제공된 Flask/OpenCV/Piper 예제를 바탕으로 반응형 화면과 여행 영어 예문 선택 기능을 구현하는 데 도움을 받았습니다. 대표 질문은 “기존 이미지 처리 3개와 form/fetch 흐름은 유지해 반응형 화면을 정리하고, TTS에는 여행 영어 예문 선택 기능을 추가해 6주차 조건에 맞게 구현해 줘”였습니다.
- 직접 수정한 부분: 이미지 실험실 화면, 여행 영어 사용 상황과 예문 세 개, 화면 문구와 디자인을 검토하고 수정했습니다.
- 실행하여 확인한 내용: HTML·JavaScript·Python 정적 검사, 이미지 처리 세 종류와 오류 응답, Piper WAV 두 문장 생성, 파형·시간·길이·크기 표시, 390px 모바일 화면과 가로 넘침을 확인했습니다. Render 배포와 휴대전화 공개 URL 확인은 남아 있습니다.
